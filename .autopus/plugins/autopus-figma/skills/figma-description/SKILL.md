# Figma Description Skill

Figma 화면을 구현 캡션이 아니라 PM, 디자이너, 개발자, QA가 함께 읽는 화면 정의/기능 정의 문서로 작성합니다.

## 핵심 원칙

- 화면 이미지만 보고 확정 정책을 만들지 않습니다. 먼저 stakeholder Q&A로 제품 목적, 사용자, 권한, 데이터, 상태, 예외를 확인합니다.
- Figma에는 최종 디스크립션만 작성합니다. 미확정 정책은 `[CANNOT_INFER]` 또는 `Open Questions`로 분리합니다.
- 디스크립션은 `Hierarchy -> Grouping -> Numbering -> Highlighting -> Case` 순서로 읽히게 작성합니다.
- 프레임은 설명 대상이 아니라 화면 컨테이너입니다. 번호 뱃지는 프레임 안의 기능, 영역, 상태 변화, 사용자 액션 대상에 붙입니다.
- `프레임 1개 = 뱃지 1개`로 만들지 않습니다. 한 프레임 안에 검색, 필터, 탭, 목록, 추천, 상세 진입처럼 개발/QA가 알아야 할 대상이 여러 개면 각각 뱃지를 붙입니다.
- 화면의 각 기능 뱃지에는 디스크립션의 같은 번호 블록이 1:1로 매칭되어야 합니다.
- 기능 번호는 프레임 내부 자식 노드로 배치합니다. 단순히 섹션 위에 떠 있는 주석이면 "프레임 안 기능 뱃지"로 보지 않습니다.
- **디스크립션 카드는 대상 프레임 바로 옆에 둡니다.** 멀리 떨어진 보드에 카드만 몰아넣지 않습니다. 카드와 프레임은 한 뷰포트에서 함께 보여야 합니다.
- 카드가 너무 요약되어 기능 의도만 남지 않게 합니다. 버튼/링크/콘텐츠/상태 변화/예외/랜딩을 생략하지 않습니다.
- 개발자가 바로 제품 로직을 설계할 수 있을 정도로 조건, 입력값, 상태 전이, 예외, QA 기준을 씁니다.
- 디스크립션은 PM, 디자이너, 개발자, QA가 같은 단어로 이해할 수 있어야 합니다. 개발자 jargon 대신 기능과 의미를 풀어 씁니다.
- API endpoint, DB schema/table/column, enum 값, 이벤트 키, 분석 키, 컴포넌트명, 파일 경로, 상태관리/캐시 키, 쿼리 파라미터 키 같은 개발자 영역의 식별자는 자작하지 않습니다. 자세한 규칙은 `용어와 표기 규칙`을 따릅니다.
- brief나 사전 자료에 dev key 형태(snake_case, camelCase, `=`/`?` 포함 토큰)가 들어 있어도 디스크립션 본문에서는 자연어로 재표현합니다. 원형 인용이 꼭 필요하면 코드 폰트로 감싸고 `(개발자 합의 후 결정될 식별자)` 같은 단서를 같이 씁니다.
- 본문에서 사용하는 영역 이름, 기능 이름, 상태 이름은 brief의 `domain_terms`/사용자가 화면에서 보는 라벨을 우선합니다. 같은 개념은 같은 표기를 끝까지 유지합니다.
- 화면에서 직접 확인되지 않고 brief에도 없는 동작은 추론으로 단정하지 않습니다. 추론이 필요한 부분은 `[추론]` 또는 `[OPEN]`으로 표기하고 본문 어조도 단정문에서 가정문으로 바꿉니다.

## 필수 선행 절차

1. Figma 노드 구조와 대표 스크린샷을 확인합니다.
2. `.autopus/runs/<project-slug>/description-brief.json`에 brief를 생성하거나 갱신합니다.
3. 사용자에게 다음을 질문합니다.
   - 이 제품은 누구를 위해 어떤 문제를 해결하는가?
   - 이 Figma 범위에서 반드시 설명할 사용자 플로우는 무엇인가?
   - 역할, 권한, 접근 제한, 다운로드/외부 링크 정책은 무엇인가?
   - 검색, 필터, 정렬, 페이지네이션, 상세 진입, reset 범위의 확정 규칙은 무엇인가?
   - loading, empty, error, disabled, permission denied, populated 상태는 어떻게 보이는가?
   - 사용자가 체감하는 데이터/갱신 주기/이벤트 의미는 무엇인가? (API 경로나 키 이름은 묻지 않습니다.)
   - 아직 추론하면 안 되는 정책은 무엇인가?
4. 답변이 부족하면 확정하지 말고 `[CANNOT_INFER]`로 남깁니다.

## 번호 뱃지 단위 선정

번호 뱃지는 "프레임 수"가 아니라 "설명해야 할 기능 단위"를 기준으로 생성합니다.

### 뱃지를 붙여야 하는 대상

- 사용자가 클릭, 입력, 선택, 닫기, 이동, 다운로드, 열람하는 액션 대상.
- 검색창, 검색 범위 드롭다운, 필터, 필터 초기화, 탭, 보기 개수, 페이지네이션처럼 목록 조회 조건을 바꾸는 컨트롤.
- 리포트 행, 우측 추천 항목, 상세 패널, 원문보기, 다운로드처럼 다음 화면이나 패널로 이어지는 진입점.
- 많이 본 리포트, 실시간 인기 종목처럼 랭킹/추천/캐시/집계 기준이 필요한 영역.
- loading, empty, error, disabled, selected, expanded, limited처럼 화면 프레임이 상태 변화를 보여주는 영역.
- 개발/QA가 "이 버튼은 무엇을 바꾸는가?", "이 값은 어디까지 유지되는가?", "예외는 무엇인가?"를 물어볼 만한 영역.

### 뱃지를 붙이지 않는 대상

- 순수 장식, 반복 배경, 아이콘만 있고 기능 의미가 없는 요소.
- 이미 다른 뱃지 설명에 포함된 반복 row의 개별 복제본. 단, row click, row action, column sort처럼 로직이 있으면 뱃지를 붙입니다.
- 프레임 자체. 프레임 번호는 그룹 제목으로만 쓰고, 기능 설명 뱃지와 혼동하지 않습니다.

### 번호 체계

- 기본 형식은 `FNN-MM`을 사용합니다. `FNN`은 화면/프레임 그룹, `MM`은 해당 프레임 안의 기능 번호입니다.
- 예: `F04-01 리포트 검색 입력`, `F04-02 검색 범위 드롭다운`, `F04-03 검색 제출`.
- 같은 기능이 여러 상태 프레임에 반복되면 동일한 기능 번호를 재사용하고 상태 suffix를 붙일 수 있습니다. 예: `F04-02a closed`, `F04-02b open`.
- 한 프레임 안의 설명 대상이 하나뿐인 경우에만 `FNN-01` 하나로 끝낼 수 있습니다.

### 뱃지 맵 작성

Figma에 쓰기 전에 brief와 Figma 구조를 기반으로 badge map을 먼저 정합니다.

- `frame_id`, `frame_name`, `frame_purpose`
- `badge_id`, `badge_label`, `target_name`, `target_reason`
- `target_type`: input, dropdown, filter, tab, list, row, ranking, panel, viewer, download, state 등
- `state_relation`: default, open, selected, applied, error, empty, loading, limited 등
- `description_scope`: 이 뱃지 설명이 포함해야 할 제품 규칙

badge map이 불확실하면 Figma에 바로 쓰지 말고 사용자에게 확인합니다.

## 용어와 표기 규칙

디스크립션은 PM, 디자이너, 개발자, QA가 함께 읽는 문서입니다. 개발자가 정의해야 할 영역을 침범하지 않고, 모든 직군이 같은 단어로 이해할 수 있게 씁니다.

### 개발자 영역 침범 금지

다음은 개발자가 코드/시스템 합의 후 정하는 영역입니다. 디스크립션에서 임의로 만들어 적지 않습니다.

- **API endpoint / HTTP 메서드** — `GET /api/reports`, `POST /v1/search` 같은 경로/메서드를 자작하지 않습니다. 대신 "리포트 목록 조회 요청", "검색 요청 전송"처럼 기능 의미만 씁니다.
- **DB 테이블 / 컬럼 / enum 값** — `users.role_enum`, `reports.status='PUBLISHED'` 같은 식별자를 자작하지 않습니다. "사용자 권한", "리포트 상태(작성 중/발행/만료)"처럼 도메인 의미로 씁니다.
- **이벤트 / 분석 키** — `report_view_clicked`, `search_submit_event` 같은 키 이름을 자작하지 않습니다. "리포트 열람 이벤트", "검색 제출 이벤트"처럼 의미만 씁니다.
- **컴포넌트 / 파일 / 상태 라이브러리 키** — `<ReportTable>`, `useReportStore`, `reports.slice.ts` 같은 식별자를 자작하지 않습니다. "리포트 목록 영역", "리포트 데이터 캐시"처럼 영역/역할로 씁니다.
- **캐시 키 / 쿼리 파라미터 키** — `cache_key=report:list`, `?q=&page=&size=` 같은 키를 자작하지 않습니다. "검색어, 페이지 번호, 페이지당 개수"처럼 의미로 씁니다.

이러한 식별자는 사용자(PM/개발자)가 이미 명시적으로 제공한 경우에만 그대로 인용하고, 출처(누가/언제 합의했는지)를 함께 표기합니다. 출처가 불분명하면 인용하지 않고 `[OPEN: 개발자 합의 필요]`로 둡니다.

### 다직군 가독성

- 영문 약어/용어를 처음 사용할 때는 한글 풀이를 병기합니다. 예: `CTA(Call to Action, 주요 액션 버튼)`, `Empty State(데이터 없음 상태)`.
- 개발 프레임워크/패턴 용어(Hook, Reducer, Slice, Mutation, Selector, Subscription, Memoization 등)는 그대로 쓰지 않고 기능 의미로 풀어 씁니다.
- "비동기", "디바운스", "메모이즈" 같은 개발 용어가 필요하면 사용자가 체감하는 결과로 바꿔 씁니다. 예: "300ms 동안 추가 입력이 없으면 검색을 실행".
- 같은 개념은 문서 내내 같은 단어로 부릅니다. 한 곳에서 `리포트`, 다른 곳에서 `보고서`로 부르지 않습니다.
- 화면 영역 명칭은 사용자에게 보이는 라벨이나 도메인 용어를 우선합니다. 라벨이 없으면 "좌측 검색 영역", "우측 추천 영역"처럼 위치+역할로 부릅니다.

### 결정 상태 라벨

본문의 각 진술이 어떤 단계에 있는지 라벨로 표시합니다. 라벨이 없는 단정문은 "확정"으로 간주됩니다.

- `[확정]` — brief의 `global_policies`/`user_rules` 또는 사용자 합의 사항으로 명시된 정책.
- `[권고]` — brief의 `interaction_rules`나 `resolved_decisions`처럼 "권고" 단서가 붙어 있거나 합의가 완료되지 않은 제안.
- `[추론]` — 화면 또는 brief에서 명시되진 않았으나 흐름상 자연스럽게 도출되는 동작. 본문 어조는 가정문("...로 보인다", "...로 보이며 확정 필요")으로 씁니다.
- `[OPEN]` — 결정이 비어 있는 항목. 항상 owner를 명시합니다. 사용 가능한 owner: `PM`, `디자인`, `개발`, `QA`, `법무/보안`. 예: `[OPEN: PM] 빈 검색어 제출 허용 여부`, `[OPEN: 개발] 검색 이벤트 키 이름`.

권고와 확정이 한 섹션에 혼재하면 각 항목 앞에 라벨을 붙여 구분합니다.

## 디스크립션 카드 구조

디스크립션의 기본 단위는 "뱃지"입니다. 카드 하나가 프레임 그룹을 나타내더라도, 카드 안에는 뱃지별 설명 블록이 독립적으로 있어야 합니다.

### 카드 헤더 메타데이터 (필수)

각 그룹 카드 최상단에는 다음 메타 블록을 둡니다. 카드-프레임 인접 책임을 명시적으로 만들기 위해 필수입니다.

```
[DESC] <flow name> Cards — <Frame Group ID>
- anchor_frame: <Figma node ID of the primary frame this card is placed next to>
- placement: 우측 / 아래 / 좌측 (기본: 우측)
- linked_badges: F04-01, F04-02, F04-03, F04-04
- card_owner: 디스크립션 작성자/검수자 이름 또는 역할
- last_updated: YYYY-MM-DD
```

- `anchor_frame`이 비어 있는 카드는 미배치로 간주하고 검증 단계에서 실패 처리합니다.
- 한 그룹 카드가 여러 상태 프레임을 묶더라도 `anchor_frame`은 가장 대표가 되는 프레임 하나만 지정하고, 다른 상태 프레임은 카드 내부 뱃지 블록에서 다시 명시합니다.

### 뱃지 블록 헤더 (필수)

각 뱃지 설명 블록 시작 줄에 뱃지 ID와 대상 노드 식별을 적습니다.

```
### F04-01 리포트 검색 입력(빈 상태)
- target_node: <Figma node ID of the actual element>
- target_frame: <enclosing frame node ID>
- decision_status: 확정 / 권고 / 추론 / OPEN  (전체 블록 기본값; 항목별로 라벨이 있으면 항목 라벨이 우선)
```

### 뱃지 본문 섹션 (이 순서로 작성)

1. `대상/역할`
   - 이 뱃지가 가리키는 UI 요소와 제품 역할을 씁니다.
   - 사용자가 왜 이 기능을 쓰는지 업무 맥락을 씁니다.
2. `진입/노출 조건`
   - 이전 화면, 트리거, 랜딩 포인트, 유지되어야 하는 컨텍스트를 씁니다.
3. `Default`
   - 최초 노출값, 선택된 값, placeholder, 비활성 여부, 기본 개수, 기본 정렬을 씁니다.
4. `입력/선택 규칙`
   - 허용 값, 옵션 목록, 다중/단일 선택, validation, reset 포함 여부를 씁니다.
5. `인터랙션`
   - `클릭`, `Enter`, `Esc`, `외부 클릭`, `hover`, `focus restore`처럼 제스처를 구체적으로 씁니다.
   - 링크는 내부 링크, 딥링크, 외부 링크, 패널, 모달, 원문 뷰어 중 무엇인지 씁니다.
6. `상태 변화`
   - 상태 이름은 한국어 라벨로 씁니다. 예: "빈 입력 상태", "포커스된 입력 상태", "결과 로딩 중", "결과 표시", "결과 없음", "오류 발생".
   - `empty_input`, `focused_input` 같은 snake_case 영어 상태 이름은 개발자 내부 state machine 영역이므로 본문에 그대로 쓰지 않습니다. brief에 영어 상태 이름이 있어도 한국어로 번역합니다.
   - 전후 변화는 화살표로 연결합니다. 예: `진입 → 빈 입력 상태 → 사용자 클릭 → 포커스된 입력 상태`.
   - Default와 액션 후 상태를 분리합니다.
7. `Case`
   - 일반 동작 아래에 `Case 1`, `Case 2` 형식으로 예외를 씁니다.
   - 데이터 없음, 권한 없음, 긴 텍스트, 네트워크 오류, 제한 초과, 동률/중복 등 QA 분기까지 포함합니다.
8. `데이터/이벤트`
   - 사용자/제품 관점의 **논리적 의미만** 씁니다. 예: "검색어, 검색 범위, 페이지 번호, 페이지당 개수, 선택된 리포트 식별".
   - 캐시/갱신 주기는 시간 의미만 씁니다. 예: "1분 주기로 자동 갱신". 캐시 키, 저장소 이름은 자작하지 않습니다.
   - 분석 이벤트도 "리포트 열람 이벤트", "검색 제출 이벤트"처럼 의미만 씁니다. 이벤트 키나 속성 키를 자작하지 않습니다.
   - brief에 `query`, `search_scope`, `popular_report_rankings` 같은 dev key 표기가 있어도 본문에서는 자연어로 재표현합니다. 원형 토큰이 꼭 필요하면 코드 폰트로 감싸고 `(개발자 합의 후 확정될 식별자)` 단서를 같이 적습니다.
   - API endpoint, DB table, enum, 이벤트 키, 컴포넌트명은 사용자가 이미 명시한 경우에만 그대로 인용하고 출처를 함께 표기합니다. 미확정이면 owner를 명시한 `[OPEN]` 라벨을 사용합니다.
9. `QA 기준`
   - 개발/QA가 확인할 수 있는 관찰 가능한 기준으로 씁니다.

## 작성 품질 기준

- 번호와 bullet을 사용하되, 카드 하나가 단순 요약 4줄로 끝나지 않게 합니다.
- 중요한 확정 정책은 굵게 또는 별도 라벨로 강조합니다.
- "선택 시"처럼 모호하게 쓰지 말고 "드롭다운 옵션 클릭 시", "검색 아이콘 클릭 시", "Enter 입력 시"처럼 씁니다.
- 링크는 내부 링크, 딥링크, 외부 링크, 원문 뷰어 중 무엇인지 구분합니다.
- 콘텐츠 목록은 노출 순서와 fallback을 씁니다.
- Hidden UI는 어떤 액션으로 노출되는지 씁니다.
- 서비스 연결성은 반드시 씁니다. 팝업인지, 패널인지, 같은 화면 갱신인지, 새 뷰어인지 구분합니다.
- 추천/랭킹/실시간 영역은 집계 기준, 중복 제거, 동률, fallback, 캐시 주기를 씁니다.
- 다운로드/크롤링 리스크가 있으면 rate limit, 제한 초과 UI, 감사 이벤트를 씁니다.

## Figma Write-back 규칙

### 카드-프레임 인접 책임

- **그룹 카드 배치**: 그룹 카드(`[DESC] ... Cards — <Group ID>`)는 헤더의 `anchor_frame`이 가리키는 프레임 바로 옆(우측 기본, 공간이 없으면 아래)에 배치합니다. 카드와 anchor 프레임은 한 뷰포트에서 함께 보여야 하며, 멀리 떨어진 보드에 카드만 몰아넣지 않습니다.
- **인접 정량 기준**: 그룹 카드의 가까운 모서리가 anchor 프레임 모서리에서 anchor 프레임 width의 1.5배 이내에 있어야 합니다. 초과하면 카드 위치를 조정합니다.
- **상태 분기 프레임 처리**: 한 카드에 default/open/empty/error 등 상태별 뱃지 블록이 묶여 있으면, 그룹 카드의 `anchor_frame`은 default 또는 사용자가 처음 보는 상태 프레임을 지정합니다. 나머지 상태 프레임은 각 뱃지 블록 헤더의 `target_frame`으로 다시 명시하여 추적 가능하게 만듭니다.
- **뱃지 노드 자체**: `[BADGE] FNN-MM <TARGET_ID>` 노드는 카드 위치와 무관하게 항상 대상 프레임 내부의 실제 자식으로 배치합니다(인접 기준의 영향을 받지 않음).
- 각 대상 프레임 내부의 기능/영역/상태 지점에 `[BADGE] FNN-MM <TARGET_ID>` 노드를 생성합니다.
- 설명 카드 또는 프레임 그룹 카드 안에도 동일한 `FNN-MM` 뱃지를 배치합니다.
- 카드 보드는 프레임별 그룹을 만들고, 각 그룹 안에 뱃지별 상세 설명 블록을 배치합니다.
- 카드 보드는 `[DESC] <flow name> Cards`로 이름 짓습니다.
- 기존 `[DESC]`/`[BADGE]` 노드를 갱신할 때는 먼저 대상 범위를 식별하고, 같은 flow 안의 이전 자동 생성물만 교체합니다.
- 뱃지는 대상 UI를 가리지 않게 배치합니다. 공간이 좁으면 프레임 내부의 가까운 여백에 두고 짧은 connector/callout으로 대상과 연결합니다.
- Figma Plugin API 사용 시 `figma-use` 스킬 규칙을 따릅니다.

### 마크다운 마커 → 시각 위계 변환

카드 본문 마크다운에는 `### 뱃지 제목`, `**섹션 헤더**` 같은 마커가 사용됩니다. 이 마커가 Figma 텍스트 노드에 plain text로 그대로 들어가면 가독성이 떨어집니다. write-back 시 마커를 제거하고 Plugin API의 `setRangeFontName` / `setRangeFontSize`로 시각 위계로 변환합니다.

- `### {제목}` — 마커 제거. 해당 범위에 SemiBold 적용 + 본문보다 1~2pt 큰 사이즈 (본문 11pt → 헤더 13pt 권장).
- `**{섹션 헤더}**` — 마커 제거. 해당 범위에 SemiBold (사이즈는 본문과 동일).
- 코드 토큰( `` `query` `` ) — backtick 그대로 유지. monospace 폰트가 없으면 backtick이 코드 표기 역할.
- bullet `- ` — 그대로 유지.
- 결정 라벨 `[확정]` / `[권고]` / `[추론]` / `[OPEN: owner]` — 그대로 유지(마크다운 마커가 아니라 의미 라벨).

#### 구현 패턴

본문을 줄 단위로 파싱하면서 헤더 위치(start/end)를 수집한 뒤 base 폰트로 전체를 설정하고 헤더 range에만 SemiBold 적용합니다.

```js
function processBody(raw) {
  const lines = raw.split("\n");
  const cleaned = [];
  const ranges = [];
  let cursor = 0;
  for (const line of lines) {
    let text = line;
    let level = null;
    if (line.startsWith("### ")) { text = line.substring(4); level = "h3"; }
    else {
      const m = line.match(/^\*\*(.+)\*\*$/);
      if (m) { text = m[1]; level = "h4"; }
    }
    if (level) ranges.push({ start: cursor, end: cursor + text.length, level });
    cleaned.push(text);
    cursor += text.length + 1;
  }
  return { text: cleaned.join("\n"), ranges };
}

// usage on a text node
const { text, ranges } = processBody(rawMarkdown);
node.fontName = fontReg;
node.fontSize = 11;
node.characters = text;
for (const r of ranges) {
  node.setRangeFontName(r.start, r.end, fontSemiBold);
  if (r.level === "h3") node.setRangeFontSize(r.start, r.end, 13);
}
```

- 생성 후 metadata와 screenshot으로 다음을 검증합니다.
  - 기능 뱃지 수와 디스크립션의 뱃지별 설명 블록 수가 일치한다.
  - 번호 뱃지가 대상 프레임 내부의 실제 자식이다.
  - 한 프레임에 필요한 기능이 여러 개이면 여러 뱃지가 존재한다.
  - **모든 그룹 카드가 `anchor_frame`을 지정하고 있고, 그 프레임 옆에서 인접 기준(1.5×width) 안에 있다.**
  - 카드 텍스트가 잘리지 않는다.
  - 기존 화면 UI를 가리지 않는다.
  - **개발자 영역 식별자(API endpoint, DB 테이블/컬럼/enum, 이벤트 키, 컴포넌트명, 캐시/쿼리 키 등)를 자작한 항목이 없다.**
  - **본문에 snake_case/camelCase 토큰이 자연어 재표현 없이 노출되지 않는다.** (예: `query`, `report_list_refresh_event`, `popular_report_rankings` 단독 노출 금지)
  - **상태 이름이 모두 한국어 라벨이다.** (예: `empty_input` 같은 dev state machine 이름 노출 금지)
  - **모든 진술이 `[확정]`/`[권고]`/`[추론]`/`[OPEN]` 중 하나로 분류 가능하고, `[OPEN]`에는 owner(`PM`/`디자인`/`개발`/`QA`/`법무/보안`)가 명시되어 있다.**

## 생성 후 자가 점검

Figma write-back을 보고하기 전에 다음 점검을 반드시 통과해야 합니다. 미통과 항목은 보고서의 "검출 결과"에 그대로 기록합니다.

1. **인접성 점검** — 모든 그룹 카드에 `anchor_frame`이 있고, 1.5×width 기준을 충족하는가?
2. **dev 식별자 자작 점검** — 본문에서 brief에 없는 새 API/엔드포인트/DB 이름/이벤트 키/컴포넌트명/캐시 키를 만들지 않았는가?
3. **dev key 노출 점검** — brief에 있던 snake_case/camelCase/`=`·`?` 포함 토큰을 자연어 재표현 없이 그대로 본문에 노출하지 않았는가?
4. **상태 이름 한국어 점검** — `상태 변화` 섹션과 본문 곳곳의 상태 이름이 모두 한국어 라벨인가?
5. **결정 라벨 점검** — 모든 진술이 `[확정]`/`[권고]`/`[추론]`/`[OPEN]`으로 분류 가능하며, `[OPEN]`에 owner가 붙어 있는가?
6. **용어 일관성 점검** — 같은 개념을 다른 카드에서 다른 단어로 부르지 않았는가?
7. **마크다운 마커 노출 점검** — Figma 텍스트 노드에 `### `, `**...**` 마커가 plain text로 남아 있지 않은가? 헤더는 `setRangeFontName` + `setRangeFontSize`로 시각 위계로 변환되어야 한다. 결정 라벨(`[확정]` 등)은 마크다운 마커가 아니므로 유지.

점검에서 걸린 항목은 보고 전에 수정하거나 Open Questions로 옮깁니다.

## 출력 형식

작업 결과를 보고할 때는 다음을 포함합니다.

- 생성/수정한 Figma 보드 노드 ID
- 카드/프레임 그룹 개수와 기능 뱃지 번호 범위

- 뱃지별 설명 블록 개수와 누락 여부
- 자가 점검 결과 7항목(통과/미통과 + 미통과 시 위치 목록)
- 카드-프레임 인접성 점검 결과(떨어진 카드 목록 또는 "충족")

- brief 파일 경로
- 미확정 Open Questions (owner 라벨 포함)
- 검증 방식
