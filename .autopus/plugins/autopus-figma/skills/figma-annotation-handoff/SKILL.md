# Figma Annotation Handoff Skill (v4)

v3의 "번호 뱃지 + 마크다운 카드" 방식을 대체한다. 같은 목적(PM·디자이너·개발·QA가 함께 읽는 화면/기능 정의)을 두 표면으로 나눠 전달한다.

## 두 표면 (locked 모델)

| 표면 | 역할 | 내용 | 어디서 보이나 |
|------|------|------|----------------|
| **네이티브 annotation** | v3 뱃지의 대체 — UI 요소별 **간단한 설명** | 요소 제목 + 한두 줄 설명 + (필요 시) 동작 | Figma **Dev Mode**에서만 (`</>` 토글 / Shift+D → 요소 선택 → 우측 Annotations) |
| **정책 카드** | 개발자가 정책을 이해하는 참조 테이블 | states / edge_cases / data_requirements / 영역별 정책 | 일반 캔버스에 노드로 노출 (`Autopus Policy Card`) |

원칙:
- 네이티브 annotation은 **각 UI 요소 노드에 직접 앵커링**한다(검색바·탭바·목록·페이지네이션·우측패널 등). 한 프레임 노드에 여러 개를 달면 덮어쓰기 되므로, 영역마다 `target_node_id`로 **서로 다른 자식 노드**를 지정한다.
- 네이티브 annotation은 **짧게**. 상태 전이·예외·데이터 규칙 같은 무거운 정책은 카드로 보낸다.
- 카드는 **실제 Figma auto-layout 테이블**(마크다운 의사 테이블 아님). 셀은 고정폭+줄바꿈으로 잘리지 않게.
- **한 화면 = canonical 카드 1개.** 같은 화면을 여러 프레임이 보일 때(예: 메인 + 상태/변형 프레임), 전체 정책의 정본은 **한 카드**로 두고 나머지 프레임 카드는 그 상태에 고유한 부분만 담거나 정본을 가리킨다. 같은 규칙을 여러 카드에 복제하면 수정 시 drift·이중작업이 난다 — 복제 대신 canonical 1곳을 고친다.

## 언어 규칙 (중요 — PM/기획자 언어)

- 본문은 **PM·기획자의 언어**로 쓴다. 개발자 jargon(Hook/Reducer/Slice/Mutation/비동기/디바운스 등)을 그대로 쓰지 않고 사용자가 체감하는 결과로 푼다. 예: "300ms 동안 추가 입력이 없으면 검색 실행"이 아니라 "입력을 멈추면 잠시 뒤 자동으로 검색"처럼.
- **dev key 자작/노출 금지**: API endpoint, DB 테이블/컬럼/enum, 이벤트 키, 컴포넌트명, 캐시/쿼리 키를 만들어 적지 않는다. brief에 snake_case/camelCase 토큰이 있어도 자연어로 재표현하고, 원형이 꼭 필요하면 코드폰트 + "(개발 합의 후 확정될 식별자)" 단서를 붙인다.
- 상태 이름은 한국어 라벨("결과 로딩 중", "결과 없음")로. `empty_input` 같은 dev state machine 이름 금지.
- 같은 개념은 같은 단어로 끝까지(리포트 vs 보고서 혼용 금지). 영역명은 화면에 보이는 라벨/도메인 용어 우선.
- **인라인 결정태그 금지**: `[확정]/[권고]/[추론]` 같은 태그를 intent·success_criteria·states·edge_cases·area 본문에 흩지 않는다. 본문은 단정형으로 깨끗하게.
- **미확정은 즉시 물어서 확정한다 (핵심)**: 정책·동작·수치·문구가 화면·brief·기존 결정으로 단정할 수 없으면, 추측하거나 `open_questions`에 쌓아두지 말고 **그 자리에서 사용자에게 직접 질문해(AskUserQuestion 등) 확정한 뒤 그 확정값으로 본문을 쓴다.** 목표는 open_questions가 비어 있는 **확정된 디스크립션**이다. 질문은 선택지를 제시해 결정 비용을 낮춘다(예: "날짜 기본값: 전체 / 최근 1개월?"). `open_questions`에는 **사용자가 명시적으로 '보류'를 택한 항목만** owner와 함께 남긴다. 한 프레임에서 미확정이 여러 개면 모아서 한 번에 묻는다.
- 디자인이 최종이면 **디자인을 정본으로** 한다. brief와 디자인이 다르면 화면(스크린샷·텍스트 노드)에서 실제 라벨/컬럼/탭을 확인해 반영한다.
- **모든 컨트롤·요소·문구·정책은 실제 렌더된 디자인에서 직접 확인하고 작성한다.** brief나 이전 버전(v3)에 있던 컨트롤이라도 현재 디자인에 없으면 쓰지 않는다(예: v3엔 '페이지 이동 입력'이 있었지만 현재 페이지네이션은 번호 막대 + 처음/이전/다음/마지막 화살표뿐 — 입력칸 없음). 어떤 요소의 존재·구성·기본값이 불확실하면 추측하지 말고 그 노드를 다시 스크린샷/메타데이터로 확인한 뒤 쓴다. 변경 이력 노트(있으면)로 무엇이 바뀌었는지 교차 확인한다.
- 문체 정본은 `src/prompts/node-only.ts`(`SYSTEM_BASE`/`HANDOFF_RULES`)다. 경제적·단정적 한국어, 한 항목 한 사실.

## ManifestEntry 작성 (schema v0.4.0)

프레임당 하나의 엔트리를 작성한다. 핵심 필드:

- `frame_id`: 앵커 프레임(카드가 이 옆에 놓임)
- `title` / `intent` / `user_value` / `success_criteria`: 프레임 수준 요약
- `area_annotations[]`: **요소별** — `{ title, target_area, description, interaction?, policy?, target_node_id }`
  - `target_node_id` = 그 UI 요소의 실제 노드 ID(검색바·탭바·목록 등). **영역마다 서로 다른 노드.** 같은 노드를 가리키는 영역은 하나로 합친다.
  - `description`/`interaction`은 네이티브 annotation(간단)에 들어가고, `policy`는 카드 테이블에 들어간다.
- `states[]`: `{ state, trigger, result }` — 카드 states 테이블
- `edge_cases[]`: `{ case, risk, handling }` — 카드 edge_cases 테이블
- `data_requirements[]`: `{ name, purpose, required_values[] }` — 카드 data 테이블
- `open_questions[]`: 미확정 결정(owner 포함)
- `write_target: "native_annotation_with_card"`

## 작성 워크플로 (결정 수집 → 작성 → 자가 리뷰 → 적용)

체크리스트는 "무엇을 담을지"다. 라운드 반복(초안→사용자가 누락 발견→수정)을 줄이려면 **순서**를 지킨다.

1. **스캔 & 결정 수집 (작성 전)**: 화면을 아래 영역 체크리스트 + D1~D7 + 마이크로 디테일로 훑어, **결정이 필요한 지점(수치·윈도우 경계·enum/옵션 전체·알고리즘·클릭 목적지·임계)을 한 번에 리스트업**한다. 이때 보조 산출물 두 개를 먼저 채운다 — (a) **인터랙션 인벤토리**: 클릭 가능한 모든 요소 → 목적지/결과, (b) **상태 매트릭스**: 비동기·조건부 표면마다 default/loading/empty/error/disabled/권한. 여기서 빈 칸이 곧 질문 목록이다.
2. **일괄 질문 (작성 전)**: 화면·brief·정본으로 단정 불가한 항목을 **모아서 한 번에** AskUserQuestion(선택지 제시)으로 확정한다. 쓰다가 하나씩 발견해 되묻지 않는다 — 이 단계를 건너뛰면 수정 라운드가 반복된다.
3. **작성**: 확정값으로 ManifestEntry를 쓴다. 사용자가 명시적으로 '보류'한 것만 `open_questions`.
4. **자가 리뷰 게이트 (사용자 핸드오프 전 필수)**: 작성한 카드 번들을 `figma-desc-reviewer`(R1~R8) 기준으로 점검한다(프레임이 여럿이면 reviewer 에이전트로 병렬 검수). **여기서 잡은 GAP을 먼저 메운 뒤** 사용자에게 넘긴다 — 갭을 사용자가 먼저 발견하게 두지 않는다.
5. **적용**: 아래 파이프라인(dryRun→approve→apply→undo).

## 적용 파이프라인 (autopus-figma MCP)

1. 엔트리를 `.autopus/dryrun-entry.json`에 작성(`frame_id` 일치 필수, dev 전용·gitignored). 없으면 dryRun이 stub.
2. `dryRun(frame_id, "native_annotation_with_card")` → 60초 TTL. plugin_commands에 요소별 `set_native_annotation` + 1× `set_policy_card`가 나오는지 확인.
3. `approve(pending_id)` → `apply(pending_id, source_hash_recomputed = dryRun의 source_hash_dryrun)`.
4. 검증: 네이티브는 Dev Mode + `get_annotations(nodeId)`, 카드는 `get_screenshot(cardNodeId)`.
5. 되돌리기: `undo(write_id)` — compound undo가 네이티브 + 카드를 함께 정리한다.

운영 주의(데몬/플러그인): [[autopus-figma-mcp-ops]]. 데몬 코드 변경 시 `npm run build` → `/mcp` 재연결 → 플러그인 Connect. 플러그인 렌더러(`autopus_policy_card_renderer.ts`) 변경 시 플러그인 재실행.

## 정책 포착 깊이 — 영역 유형별 체크리스트

핵심 원칙: **데이터가 가공(집계·순위·추천·캐시·필터·페이지네이션·정렬)되면, "무엇을 어떻게 모아서, 어떤 규칙으로 보여주는가"를 반드시 카드의 정책/데이터 테이블에 명시한다.** 화면에 직접 안 보이는 백엔드/산정 규칙이라도 brief나 PM 결정으로 정해졌으면 단정형으로 잡고, 미확정이면 `open_questions`에 owner와 함께 남긴다. "추천 영역" "집계 데이터" 같은 뭉뚱그린 표현으로 끝내지 않는다.

### 순위·추천·집계 영역 (예: 실시간 인기 종목, 많이 본 리포트)
빠짐없이 확인할 항목:
- **집계 대상**: 무엇을 세는가(열람/검색/상세 진입/원문보기/패널 클릭)와 항목별 가중치
- **집계 윈도우**: 기간(예 최근 24시간 / 30·60분), 롤링 여부, 직전 구간 fallback 사용 여부
- **갱신·캐시 주기**: 실시간 계산 vs N분 캐시(요청마다 재계산하지 않는지)
- **순위 산정**: 점수 공식/가중합산, 노출 개수(Top N)
- **중복 제거·정규화**: 동일 사용자 반복 카운트 쿨다운, 종목 표준 ID 정규화·동의어 처리
- **최소 노출 임계**: 소수 행동이 노출되지 않게 하는 threshold
- **동률 처리**: 정렬 우선순위(최근 이벤트 시각 → 발행일 → 이름 등)
- **표기**: 순위 번호, 기준 시각("YY.MM.DD 기준") 노출 위치
- **개인화 여부**: 개인 행동 기반인가 전체 집계인가
- **클릭 동작**: 항목 클릭 시 이동/적용 대상(상세 패널 / 조건 적용 목록)

### 페이지네이션·보기 개수
- 페이지 크기 옵션과 기본값(해상도/뷰포트별 차이 포함)
- 보기 개수 변경 시 현재 페이지 처리(유지 vs 1로 리셋)
- 번호막대 표기 규칙: 현재±N, 처음/끝 고정, `…` 생략
- 마지막 페이지 초과 입력 보정(자동 보정 vs 차단)
- 페이지 이동 입력 방식, 총 건수 표기

### 필터·검색
- 기본값, 옵션 목록, 단일/다중 선택
- 변경 시 페이지 리셋 범위, 초기화 대상/비대상(무엇은 유지되는가)
- 다중 선택 라벨 축약(+N), 긴 라벨 말줄임
- 검색 범위, 제출 트리거, 자동완성·디바운스 여부, IME 처리

### 목록·컬럼
- 컬럼 구성의 조건부 노출(탭/상태/카테고리별로 달라지는가)
- 정렬 가능한 컬럼과 기본 정렬 방향
- 빈 값 표기(예 `—`), 말줄임 기준, 행/제목 인터랙션

### 상세·뷰어
- 상태/카테고리별 표시 차이(어떤 필드가 빠지고 더해지는가)
- 빈·없음 상태 표기(예 투자의견 '없음' 뱃지)
- 비교/분포 위젯의 기준 기간·산정, 다운로드·원문 제한(rate limit·쿨다운)

### 상태·예외
- loading/empty/error/disabled/권한 각각의 트리거와 결과
- 데이터 부족 시 빈 상태 vs 직전 구간 fallback 중 무엇인가

### 자주 놓치는 마이크로 디테일 (필수 체크 — 실전에서 빠진 사례)
아래는 영역 체크리스트가 있어도 실제로 자주 누락되는 항목이다. 해당 영역이 있으면 **반드시** 카드에 담거나, 모르면 물어서 확정한다.
- **클릭/이동 대상**: 추천·목록·칩 등 클릭 가능한 모든 항목이 "클릭하면 어디로/무엇이 적용되나"를 명시했는가. (예: 인기 종목 클릭 → 그 종목으로 필터된 목록인지 종목 검색인지) — 추천 영역에서 특히 잘 빠진다.
- **카운트 이벤트 정의**: "조회수·열람·인기"를 셀 때 **무슨 행동을 1회로 세는가**(목록 노출 / 행 클릭=상세 진입 / 원문보기 등). "조회수"만 적고 정의를 비우지 않는다.
- **윈도우·기간의 경계 의미**: "최근 24시간 / 최근 1개월 / 최근 3개월"은 rolling인지, 기준일(발행일/이벤트시각)이 무엇인지, 포함 경계·타임존(KST 등)을 함께 적는다. 숫자만으론 부족하다.
- **표기 granularity vs 갱신주기 정합(D5)**: "N분 주기 갱신"인데 화면 기준시각을 날짜만 표기하면 모순이다. 갱신 주기와 표기 단위를 일치시킨다.
- **옵션 전체 열거(D4)**: 보기 개수·검색 범위·정렬 등 선택 옵션은 화면에 보인 일부가 아니라 전체 목록을 적거나 정본을 가리킨다.
- **정렬 가능 컬럼**: 기본 정렬 방향뿐 아니라 **어떤 컬럼이 클릭 정렬 가능한지**를 명시한다.
- **자동완성/검색 결과 범위·개수**: 무엇이 후보로 뜨나(종목만? 리포트도?), 최대 몇 건인가.
- **값 단위**: 컬럼·수치의 단위(분량=페이지 수? 금액=원? 점수 단위)를 표기한다.
- **임계·버킷 수치**: rate limit·랭킹 임계·보조 버킷(조직/IP)의 구체 횟수까지. 일부 버킷만 적고 나머지를 비우지 않는다.

확정된 항목은 카드 정책 테이블에 단정형으로 쓴다. 산정·집계처럼 화면에 안 드러나고 아직 합의 안 된 항목은 **추측으로 수치(윈도우·가중치·임계)를 단정하지 말고, 그 자리에서 사용자에게 물어 확정**한다(선택지 제시). 사용자가 보류를 택한 것만 `open_questions`에 owner와 함께 남긴다.

## 생성 후 자가 점검

1. 네이티브 annotation이 **요소별로 서로 다른 노드**에 붙었고 덮어쓰기 없는가(영역 수 = 노드 수)?
2. 네이티브 라벨이 **짧은 UI 설명**인가(무거운 정책은 카드로 갔는가)?
3. 카드 4테이블이 잘림 없이 줄바꿈되는가?
4. dev 식별자 자작/노출 0건, 상태 이름 한국어인가?
5. 본문에 인라인 결정태그가 없고, 미확정 항목은 **사용자에게 물어 확정**했는가? open_questions에는 사용자가 보류를 택한 것만 남았는가(가능하면 0건)?
6. 디자인과 본문(탭·컬럼·라벨·문구)이 일치하는가?
7. 용어 일관성 — 같은 개념 같은 단어인가?
8. **가공 규칙 깊이** — 순위·집계·추천·페이지네이션·정렬·캐시 영역에 대해 "어떻게 모으고 어떻게 보여주는가"(집계 대상·윈도우·갱신주기·순위 산정·동률·중복제거·임계·표기·클릭 동작 / 페이지 크기·번호막대·초과 보정)가 정책으로 잡혔는가? 뭉뚱그리지 않았고, 미확정 산정치는 추측 단정 대신 open_questions로 분리했는가?
9. **구현 가능성(Developer Readiness)** — "개발자가 이 카드만 보고 추측 없이 PR을 열 수 있는가?"를 묻는다. PM 언어 규율(4번)과 충돌하지 않게, dev 키 자작이 아니라 *결정이 필요한 지점이 비어 있지 않게* 한다.
   - D1 수치·단위·경계: 윈도우(rolling/fixed)·reset 시점·기간(오늘 포함·타임존)·디바운스 지연·임계·동률 정렬 등 숫자가 필요한 규칙을 자연어("실시간" 등)로 숨기지 않았는가
   - D2 상태 기계: 요소별 loading/empty/error/disabled/권한 전이가 트리거·결과와 함께 있는가
   - D3 단일 쿼리 계약: 검색·필터·탭·페이지 결합 시 전체 파라미터 집합·우선순위가 한 곳에 모여 있는가
   - D4 열거/분류 참조: enum·taxonomy·옵션 목록을 열거하거나 정본 소스를 가리키는가
   - D5 내부 모순 0: 카드 간/내 규칙 충돌(임계 없음 vs 빈상태, 통합오류 vs 재시도 등)이 없는가
   - D6 산정·렌더 결정성: 마커 위치·분포 1건·번호막대 윈도잉 등 재현 가능한 알고리즘으로 기술됐는가
   - D7 고도 명시: 카드가 "PM 핸드오프이며 데이터 계약(필드·타입·엔드포인트)은 별도"임을 밝히고 그 위치를 가리키는가(의도된 deferral ≠ 누락). D1~D6의 미확정 값은 추측 단정 대신 사용자에게 물어 확정하거나 open_questions로 분리한다.
10. **인터랙션 인벤토리** — 클릭 가능한 모든 요소(항목·버튼·칩·링크·'더보기' 등)의 목적지/결과가 빠짐없이 적혔는가(목적지 미정의 0건)?
11. **상태 매트릭스** — 비동기·조건부 표면마다 default/loading/empty/error/disabled/권한이 트리거·결과와 함께 있는가? 로딩이 한 영역에만 있고 나머지(상세·뷰어·필터 적용)는 빠지지 않았는가?
12. **카드 정합(중복 화면)** — 같은 화면을 여러 카드가 기술할 때 규칙이 일치하는가? canonical 카드 1곳을 정본으로 두고 복제 drift가 없는가?
