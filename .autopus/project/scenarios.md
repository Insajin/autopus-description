# Scenario Context

> Generated by `@auto setup --auto` on 2026-05-08.

## Scenario 1: Fixture Read To Partial Manifest

1. Operator runs `figma-read <file_id> --fixture <path> --out <manifest>`.
2. The pipeline reads frame metadata and screenshots from fixture data.
3. Oversize frames are downscaled or skipped with audit status.
4. Output is a deterministic partial manifest plus audit JSONL.

Success indicators:

- Output manifest uses the expected schema version.
- Frames are sorted by `screen_id`.
- Token patterns are redacted from stdout/stderr.
- Source hashes are deterministic across repeated fixture runs.

## Scenario 2: Description Generation

1. Operator runs `generate-descriptions <input-dir> <output-manifest>`.
2. Provider is selected with `--provider=mock|anthropic|openai`.
3. Routing chooses node-only or vision-assisted generation.
4. Manifest is written and audit output is captured.

Success indicators:

- Mock provider produces fixture-stable output.
- Anthropic/OpenAI providers require their API key environment variables.
- Confidence, persona tags, token usage, and write target fields validate.
- Batch and realtime lanes produce contract-equivalent manifests where expected.

## Scenario 3: PM Review UI

1. Operator starts `apps/review-ui` with `REVIEW_MANIFEST_PATH`.
2. PM reviews frame rows, persona views, stale badges, and token usage.
3. PM applies a selected write target or sends feedback/escalation.
4. PM can undo a previously applied write.

Success indicators:

- Missing manifest path shows an empty configuration state.
- Valid manifest renders frame dashboard.
- Apply/undo routes write audit rows.
- Slack escalation only activates when `SLACK_BOT_TOKEN` is configured.

## Scenario 4: MCP Stdio Client

1. Operator builds and links the package.
2. External client registers `autopus-mcp-stdio`.
3. Client lists resources and tools.
4. Client performs `dryRun -> approve -> apply -> undo`.

Success indicators:

- Resource list includes active selection, pending descriptions, audit events, stale frames, pending writes, and applied writes.
- Tool list preserves 4 read tools followed by 5 write tools.
- `client_profile_attached` audit is emitted once per initialize.
- `apply` fails safely when plugin bridge is not connected.

## Scenario 5: MCP HTTP/SSE Client

1. Operator runs `autopus-mcp-http --port=<port>`.
2. Client initializes a session at `/mcp`.
3. Client reuses the MCP session id for subsequent requests.
4. Pending write state remains isolated per session.

Success indicators:

- Default bind is loopback.
- Non-loopback bind requires `--allow-remote`.
- Invalid or missing session id is rejected.
- HTTP response and SSE text are redacted.

## Scenario 6: Daemon Selection Telemetry

1. Operator starts `autopus-daemon start`.
2. Figma plugin connects through token-gated bridge.
3. Selection changes publish active frame resources.
4. Telemetry and audit append under `.autopus/`.

Success indicators:

- Session token is printed once and not persisted to state file.
- `.autopus/daemon-state.json` excludes secrets.
- Recent selections update `autopus://active_selection`.
- Stale frame tracking changes only when source hashes drift.
